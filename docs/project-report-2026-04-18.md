# 專案進度與待決策事項報告

**日期：** 2026-04-18
**專案：** tcsh-web-ar — 大型互動藝術裝置的 Web AR 體驗
**目的：** 整理目前討論結果、鎖定的技術決策、以及待策展方確認的關鍵
問題，作為後續討論的依據。

---

## 1. 專案概述

`tcsh-web-ar` 是一個 Web 平台（非原生 App），讓觀展者用手機瀏覽器
進入，在大型藝術裝置現場透過鏡頭體驗三種模式。核心價值是：
**無需下載 App、無需註冊帳號**，掃 QR code 即可使用。

### 1.1 三種使用者模式

**Mode A — 現場 AR 體驗**
- 使用者進入展場，掃入口 QR code 進入網站。
- 以入口為起點，鏡頭對準作品上的物件時，網站將貼圖疊加上去。
- 作品上約有 200 至 300 個可獨立互動的物件。
- 貼圖資源採用 lazy load，避免裝置負擔過重。

**Mode B — 手持 3D 檢視**
- 同一個網站切換模式，顯示整件作品的完整 3D 模型。
- 模型帶有所有貼圖。
- 支援手勢縮放、旋轉、調整大小。

**Mode C — 創作者後台**
- 透過經 hash 混淆的密徑 + 登入進入（例如 `/_studio/<token>`）。
- 可上傳貼圖、指派到物件、微調 UV transform。
- 公開 UI 完全沒有切換到後台的入口。

| 項目 | 選擇 | 主要原因 |

| 框架 | React 19 + Vite | 團隊熟悉 React，Vite 對 SPA 輕量 |

| 資料取得 | TanStack Query | React 生態主流 |

| 項目 | 選擇 | 主要原因 |

| 語言 | Python 3.12 | 團隊偏好 |
| 框架 | FastAPI | 自動產生 OpenAPI 文件、型別安全、async 支援 |
| 依賴管理 | Poetry | 團隊偏好 |

## 3. 關鍵待決策事項：AR 追蹤策略

這是目前**最大的未決問題**，會直接影響 Mode A 是否可行。

### 3.1 現場條件摘要（策展方提供）

- 展示地點為**戶外**，自然光環境，光線會隨天候與時段變化。
- 作品主體為**單色**，但具有可辨識的立體形狀。
- 作品規模大，表面或周邊有 200 至 300 個獨立物件。
- **作品本體不可加裝任何視覺 marker**，整體需保持「無痕」。
- 入口會提供 QR code 供使用者進入網站（非持續可見）。

### 3.2 這組條件的技術挑戰

「戶外 + 單色 + 無 marker + 200-300 物件精準對位 + iOS Safari 支援」
六個條件同時滿足，**超出免費開源 WebAR 套件的能力範圍**。主要原因：

- 單色與戶外光線會讓以影像特徵為基礎的追蹤（如 MindAR）難以穩定運作。
- iOS Safari 至今（2026-04）不支援 WebXR，排除了免費的 WebXR anchor
  方案對 iPhone 使用者的可行性。
- 無 marker 的戶外 SLAM 目前仍以商業 SDK 為主。

### 3.3 三種可行路線比較

#### 路線 A — 商業 WebAR 平台（如 8th Wall / Niantic Lightship VPS）

**做法：** 採用商業 SLAM WebAR 平台做無 marker 的視覺錨點追蹤。

| 面向 | 評估 |
| --- | --- |
| iOS + Android 支援 | 支援（平台自帶跨瀏覽器 runtime） |
| 戶外運作穩定度 | 高（Niantic 為 Pokémon GO 背後團隊） |
| 無 marker 需求 | 滿足 |
| 技術風險 | 低 |
| **成本** | **約 USD 3,000 至 5,000 / 年起跳**，隨使用量上升 |
| 技術綁定 | 高（之後更換需重寫相關模組） |

#### 路線 B — MindAR 以整件作品為 image target

**做法：** 拍攝作品正面照作為 MindAR 的訓練 target，使用者走到特定
位置時觸發識別。

| 面向 | 評估 |
| --- | --- |
| iOS + Android 支援 | 支援 |
| 戶外運作穩定度 | 低至中等（光線變化敏感） |
| 無 marker 需求 | 滿足 |
| 技術風險 | 高（辨識成功率不穩定） |
| 成本 | 開源免費 |
| 逐物件精準對位 | 困難，僅能做整體疊加 |

**預期成功率：** 依光線條件約 30% 至 50%。需要使用者配合站在特定
角度距離才會觸發。

#### 路線 C — 重新設計體驗：以 QR 定位加 IMU 導覽為主

**做法：** 放棄「貼圖疊在實體作品上」的真實 AR 幻覺，改為以手機畫面
呈現虛擬作品，並透過陀螺儀與方位感測器提示使用者在場地中的位置。

| 面向 | 評估 |
| --- | --- |
| iOS + Android 支援 | 全面支援 |
| 戶外運作穩定度 | 高（不依賴視覺） |
| 無 marker 需求 | 滿足 |
| 技術風險 | 低 |
| 成本 | 開源免費 |
| 體驗本質 | 不是傳統定義的 AR，較接近「數位導覽」 |

**體驗轉變：** 使用者不再把鏡頭對準實體作品，而是在手機上看虛擬作品，
並配合方向提示（例如「物件 042 在你右前方」）來導覽。

### 3.4 建議

依據不同情境給出建議：

- **若專案有年度技術授權預算**（USD 3K–5K 起）：採用**路線 A**。
  這是能夠完整實現原始構想的唯一可靠方案。

- **若預算有限、但仍希望保有 AR 感**：採用**路線 B**，並在展場現場
  設置明確的「最佳觀賞位置」提示，引導使用者到 MindAR 識別成功率
  較高的角度與距離。適合作為概念驗證或短期展演。

- **若專案定位偏向穩定、可靠、觸及廣泛觀眾**：採用**路線 C**，重新
  設計體驗。對戶外公共藝術而言，觀眾不需要一直對準作品反而較友善，
  且在 iOS 與 Android 上皆能穩定運作。

## 4. 需要策展方決定的兩個問題

以下決定會直接影響後續技術選型與開發範圍，請協助確認：

1. **預算面：**
   是否有每年 USD 3,000 至 5,000 起的技術授權預算可編列？

2. **體驗面：**
   以下哪個方向比較符合策展理念？

   - (a) 真實 AR：貼圖疊在實體作品上的沉浸式體驗（高技術成本或高
     穩定性風險）。
   - (b) 數位導覽：手機畫面呈現虛擬作品，以方向提示與互動為主
     （穩定、免費、體驗定位不同）。

這兩題的組合會決定我們走哪條路線：

| 預算 | 體驗偏好 | 建議路線 |
| --- | --- | --- |
| 有 | 真實 AR | A（8th Wall） |
| 無 | 真實 AR | B（MindAR，接受不穩定） |
| 任何 | 數位導覽 | C（重新設計 UX） |

## 5. 其他已規劃事項

- 貼圖檔案放於 Supabase Storage，metadata 放於 Postgres。
- 貼圖採 lazy load，避免 200-300 個物件同時載入造成效能問題。
- Mode C 後台透過 Supabase Auth 登入，API 驗證 JWT。
- 整套可以用 Docker 一鍵啟動（`make docker-up`），方便後續部署。

---

## 6. 時程影響

WebAR 追蹤策略的決策會影響到：

- **Mode A 的開發時程：** 路線 B 與 C 約可在 4-6 週內完成原型；
  路線 A 需要額外整合時間（約 6-8 週）。
- **展前實測需求：** 不論哪條路線，建議至少保留 2 週現場實測期間。
- **備援計畫：** 路線 B 的辨識不穩定風險需要在 UX 上預先設計
  （例如顯示「請調整角度重試」的提示）。

## 7. 下一步

在策展方回覆前述兩個問題之前，技術團隊會進行以下不受影響的工作：

- Mode B（3D 檢視）原型：載入 glTF 模型並實作手勢操作。
- 後端資料庫建置：建立 artworks、objects、textures、placements 等
  資料表與遷移腳本。
- 後端身分驗證：實作 Supabase JWT 驗證機制。
- Mode C 後台基礎：貼圖上傳與 placement 編輯器雛形。

以上工作完成後，一旦 AR 追蹤路線確認，即可接續開發 Mode A。
